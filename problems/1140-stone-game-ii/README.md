# 1140. Stone Game II

- Difficulty: medium
- Link: https://leetcode.com/problems/stone-game-ii/
- Topics: Array, Math, Dynamic Programming, Minimax, Prefix Sum, Game Theory, Zero-Sum Game
- Acceptance: 73.6%

## Statement

Alice and Bob continue their games with piles of stones. There are a number of piles **arranged in a row**, and each pile
has a positive integer number of stones `piles[i]`. The objective of the game is to end with the most stones.

Alice and Bob take turns, with Alice starting first.

On each player's turn, that player can take **all the stones** in the **first** `X` remaining piles, where `1 <= X <= 2M`.
Then, we set `M = max(M, X)`. Initially, M = 1.

The game continues until all the stones have been taken.

Assuming Alice and Bob play optimally, return the maximum number of stones Alice can get.

**Example 1:**

**Input:** piles = [2,7,9,4,4]

**Output:** 10

**Explanation:**

- If Alice takes one pile at the beginning, Bob takes two piles, then Alice takes 2 piles again.
  Alice can get `2 + 4 + 4 = 10` stones in total.
- If Alice takes two piles at the beginning, then Bob can take all three piles left.
  In this case, Alice get `2 + 7 = 9` stones in total.

So we return 10 since it's larger.

**Example 2:**

**Input:** piles = [1,2,3,4,5,100]

**Output:** 104

**Constraints:**

- `1 <= piles.length <= 100`
- `1 <= piles[i] <= 10^4`

## Hints

<details><summary>Hint 1</summary>

Use dynamic programming: the states are (i, m) for the answer of piles[i:] and that given m.

## Idea

### Постановка

Игра конечная, с полной информацией и нулевой суммой: сумма очков обоих равна `sum(piles)` и не зависит от хода игры, поэтому выигрыш одного ровно равен проигрышу другого. Значение позиции считается обратной индукцией от терминальной.

Камни берутся только с начала ряда, поэтому оставшиеся кучи всегда образуют суффикс `piles[i:]`. Но, в отличие от [1406. Stone Game III](https://leetcode.com/problems/stone-game-iii/), одного индекса мало: набор доступных ходов зависит от `M`, а `M` меняется по ходу игры. Позиция — пара `(i, M)`.

**Почему пары достаточно.** Правила ссылаются на историю только через `M = max` всех сделанных ходов, а `M` пересчитывается из предыдущего `M` и текущего `X`. Значит `(i, M)` — марковское состояние: две партии, пришедшие в одинаковые `(i, M)` разными путями, дальше неотличимы. Накопленные очки и номер игрока в состояние не входят — правила симметричны, а очки лишь сдвигают ответ на константу.

Число состояний `O(n²)`, а не `2ⁿ`: разные последовательности ходов, снявшие одинаковое число куч с одинаковым максимумом, сходятся в одну позицию.

### Функция ценности

Здесь удобнее считать не перевес, а **долю ходящего**:

```text
f(i, m) = максимум камней, которые заберёт игрок, делающий ход
          на суффиксе piles[i:] при текущем M = m,
          при условии оптимальной игры соперника
```

Причина отойти от negamax-перевеса из 1406 — в том, что ответ задачи и есть доля (`maximum number of stones Alice can get`), а сумма суффикса известна заранее. Обе величины эквивалентны: `f_доля = (suffix[i] + f_перевес) / 2`; выбор — вопрос того, что не придётся пересчитывать в конце.

### Рекуррентное соотношение

Взяв `X = x` куч, ходящий получает `piles[i] + … + piles[i+x−1]` и оставляет сопернику позицию `(i+x, max(m, x))`. Соперник заберёт из остатка `f(i+x, max(m, x))`, а весь остаток стоит `suffix[i+x]`, значит ходящему из остатка достанется `suffix[i+x] − f(i+x, max(m,x))`. Складывая со взятым и сворачивая `piles[i..i+x−1] + suffix[i+x] = suffix[i]`:

```text
f(i, m) = max( suffix[i] − f(i+x, max(m, x)) ),  x = 1..2m, i+x <= n
f(n, m) = 0
```

Взятое в формулу не входит явно — оно уже внутри `suffix[i]`. Отсюда полезное прочтение: ходящий не выбирает, сколько взять, а выбирает, **сколько оставить сопернику** — и минимизирует его долю.

Правая часть зависит только от бо́льших `i`, поэтому соотношение корректно определяет `f` индукцией по `n − i`. Ответ — `f(0, 1)`.

### База отсечения

Если `2m >= n − i`, ходящий может забрать весь остаток одним ходом, и `f(i, m) = suffix[i]`: больше суффикса не получить, а столько — получить можно. Это не оптимизация, а вторая база рекурсии; без неё пришлось бы отдельно следить, что `max(m, x)` не вылезает за размер таблицы. Заодно отсюда видно, что `m > n/2` бессмысленны: все такие состояния разрешаются мгновенно.

Функция не убывает по `m` — больший `M` лишь добавляет ходов, не отнимая старых. В таблице ниже это видно по строке `i = 0`: `10, 22, 26, 26, 26`.

### Почему жадность неверна

«Брать больше» оценивает только немедленный выигрыш и игнорирует, что `M = max(M, X)` — это ещё и подарок сопернику: большой ход расширяет его возможности на весь остаток игры. Пример 1 из условия показывает ровно это: `X = 2` даёт Алисе `9`, а `X = 1` — `10`.

Резче тот же эффект на `[1,1,1,100]` (тест `small move keeps the big pile`): `X = 2` оставляет Бобу `(2, M=2)`, откуда он забирает всё оставшееся, включая `100`, и Алиса получает `2`. Ход `X = 1` держит `M = 1`, и у Боба обе альтернативы плохи — он берёт максимум две кучи по `1`, после чего `100` достаётся Алисе: `101`. Симметрично неверна и обратная жадность «брать поменьше»: на `[1,2]` минимальный ход отдаёт сопернику `2`.

### Проверка на примере 1

`piles = [2,7,9,4,4]`, `suffix = [26,24,17,8,4,0]`. Достижимы только `m <= max(1, i)` — чтобы `M` стало больше стартовой единицы, кто-то должен был снять `m` куч, — поэтому таблица разрежена; ниже — состояния оптимальной линии:

| состояние | варианты `suffix[i] − f(next)` | `f`    |
| --------- | ------------------------------ | ------ |
| `(4, ·)`  | `4 − 0`                        | 4      |
| `(3, 2)`  | `8 − 4`, `8 − 0`               | 8      |
| `(2, 1)`  | `17 − 8`, `17 − 4`             | 13     |
| `(1, 1)`  | `24 − 13`, `24 − 8`            | 16     |
| `(0, 1)`  | `26 − 16`, `26 − 17`           | **10** |

Линия читается сверху вниз: Алиса берёт одну кучу (`2`), Боб — две (`7+9 = 16`), после чего `M = 2` позволяет Алисе забрать хвост целиком (`4+4 = 8`). Итого `2 + 8 = 10` против `16` — совпадает с разбором в условии.

### Сложность

Состояний `O(n²)`, перебор хода в каждом — до `2m = O(n)`, итого `O(n³)`, при `n = 100` порядка `10⁶` операций. Память `O(n²)`.

Верхняя оценка сильно пессимистична. Два ограничения — `m <= max(1, i)` и `2m < n − i` (иначе состояние разрешается мгновенно) — вырезают из квадрата решётки почти всё: при `n = 100` реально считаются около 1700 состояний из 10 000. Отсюда выбор реализации.

Свернуть таблицу в одну строку, как в задачах на отрезки, не выйдет: `f(i, m)` тянется к строке `i + x` для всех `x` сразу, а не к соседней.

### Реализация

Рекурсия с мемоизацией сверху вниз, а не заполнение таблицы снизу вверх. Причина не в красоте, а в том самом разрежении: восходящий обход либо считает недостижимые состояния впустую, либо требует руками выписывать границу `m <= min(max(1, i), (n−i−1)/2)`. Ленивый обход берёт ровно достижимое даром — из `(0, 1)` просто некуда попасть в остальные.

Таблицы вынесены в пакет как массивы фиксированного размера `[101][101]`: при `n <= 100` размер известен заранее, а на LeetCode одна отправка прогоняет десятки тестов, и переаллокация `O(n²)` на каждый — чистые накладные расходы.

Отсюда возникает вопрос очистки: между вызовами таблица хранит чужие значения. Обнулять `10⁴` ячеек — ровно та работа, которой мы избегали. Вместо этого рядом лежит массив `seen` с **номером поколения**: `generation` увеличивается на входе, запись считается своей, только если `seen[i][m] == generation`. Старые значения не удаляются, а перестают опознаваться.

Тот же приём можно уложить в одно слово, упаковав значение и поколение в биты (`win | gen`, чтение через `& MASK`). Это ещё чуть быстрее, но связывает корректность с тем, что ответ не превысит выбранную границу: при `MASK = 2²⁰ − 1` запас над максимумом задачи `100 × 10⁴` всего 4.8%, и выход за него портит ответы молча. Отдельный массив меток стоит около 1.6% времени и снимает ограничение полностью.

Замеры на `n = 100`, `-count=10`, оба варианта в одном бинарнике (`benchstat`, `p = 0.000`):

| реализация                                      | время     | аллокации   |
| ----------------------------------------------- | --------- | ----------- |
| восходящая, вся таблица, `make` на каждый вызов | 118.3 мкс | 94 КБ / 103 |
| восходящая, только достижимые `(i, m)`          | 68.4 мкс  | 94 КБ / 103 |
| нисходящая с поколениями (текущая)              | 53.8 мкс  | 0           |

Из −55% примерно две трети даёт отказ от счёта недостижимых состояний, остальное — нулевые аллокации и переиспользование таблицы.

Плата за глобальные массивы — функция перестаёт быть чистой: параллельные вызовы её сломают, а в тестах нельзя `t.Parallel()`. Регрессия на переиспользование таблицы между вызовами вынесена в отдельный тест.

### Замечания

При `n <= 9` задача решается перебором без мемоизации — в тестах он служит независимым эталоном. Эталон написан от определения задачи: каждый игрок максимизирует собственную добычу, а не разность, — чтобы не разделить с решением возможную ошибку в переходе.

Шаблон `max(взятое − ценность остатка для соперника)` тот же, что во всём семействе Stone Game; новизна 1140 в том, что в состояние входит не только позиция, но и параметр правил.
