# Count Valid Substrings

- Link: задача контестная; название и слаг взяты из имени функции `countValidSubstrings` и могут отличаться от настоящих
- Contest: номер, сложность и ссылка на момент решения не опубликованы

## Statement

You are given a string `s` consisting only of the characters `'a'`, `'b'`, and `'c'`.

A string is called **valid** if it does not contain `"abc"` as a **substring**.

Return the number of **valid substrings** in `s`. Substrings with different starting or ending indices are counted separately.

A **substring** is a contiguous **non-empty** sequence of characters within a string.

**Example 1:**

```
Input: s = "abac"
Output: 10
```

**Example 2:**

```
Input: s = "abc"
Output: 5
```

**Example 3:**

```
Input: s = "ac"
Output: 3
```

**Constraints:**

- `1 <= s.length <= 10^5`
- `s` only consists of `'a'`, `'b'`, and `'c'` characters.

## Idea

Подстрок O(n²), перебирать их нельзя: при `n = 10^5` это `5 * 10^9`. Но свойство «нет `abc`» устроено просто: если подстрока плохая, то плохая и любая её надстрока. Поэтому при фиксированном правом конце `right` допустимые левые концы образуют непрерывный хвост, и считать надо только его длину.

Подстрока `s[left..right]` плоха тогда и только тогда, когда внутри неё целиком лежит вхождение `abc`, то есть `left <= last`, где `last` — начало самого правого вхождения, закончившегося не позже `right`. Значит, хороших левых концов ровно `right - last`. Если вхождений ещё не было, `last = -1`, и формула даёт все `right + 1` подстрок.

Каждая подстрока однозначно задаётся своим правым концом и левым, поэтому сумма по `right` считает каждую ровно один раз. Двух указателей и счётчиков окна здесь не нужно: граница определяется одним запомненным индексом. Ответ достигает `5 * 10^9`, он не влезает в `int32`; для этого есть тест на `10^5` символов.

Сверка с перебором всех подстрок идёт на 20 000 случайных строк длиной до 12 символов. Варианты дополнительно сверяются между собой на входах максимальной длины.

Варианты замерены в одном бинарнике (`benchstat`, `-count=20`, Apple M2 Pro, `n = 10^5`, аллокаций нет ни у кого):

| Вход        | скан, `s[r-2:r+1] == "abc"` | скан, три сравнения байтов     | `strings.Index` и формула |
| ----------- | --------------------------- | ------------------------------ | ------------------------- |
| `random`    | 165.6 мкс                   | 402.6 мкс ± 13% (+143%)        | 283.4 мкс ± 14% (+71%)    |
| `all-abc`   | 103.8 мкс                   | 102.5 мкс (-1.3%, `p = 0.033`) | 159.6 мкс (+54%)          |
| `no-abc-ab` | 104.7 мкс                   | 89.6 мкс (-14%)                | 59.7 мкс (-43%)           |
| `all-a`     | 90.5 мкс                    | 89.4 мкс (-1.1%)               | 29.5 мкс (-67%)           |

Там, где `p` не указан, `p = 0.000`.

Выбран скан со срезом: у него лучший худший случай и самый короткий код. `strings.Index` быстрее только там, где вхождений мало, и заметно проигрывает, когда они есть. Побайтовый вариант немного выигрывает на предсказуемых входах и более чем вдвое проигрывает на случайном. Вероятная причина — ошибки предсказания ветвлений на цепочке `&&`, но это гипотеза: счётчики процессора я не снимал.

При этих ограничениях разница несущественна: все варианты укладываются в 0.5 мс.

- Time: O(n)
- Space: O(1)
